# Stack de banco de grafos + GraphRAG para o "insight engine" (single-user, local-first, Windows 11, Claude)

Notas de pesquisa — 2026-11-07. Escopo: substituir o vault Obsidian (~2.900 notas) por um grafo de conhecimento em Python com ingestão de 50–300 itens/dia, extração por LLM (Anthropic), embeddings, detecção de comunidades, validade temporal, proveniência e motor de ideias. Versões, limites e licenças foram verificados em fontes primárias (PyPI/npm JSON, GitHub API, docs oficiais) nesta data; itens marcados **[incerto]** vieram de fontes secundárias ou não puderam ser confirmados. Pesquisa web (WebSearch) esgotou a cota da sessão na rodada final; as últimas verificações usaram apenas fetch direto de URLs conhecidas.

## KQ1 — Bancos de grafos: embutido vs servidor, licença, Cypher, vetores, algoritmos, visualização, maturidade Python

### Takeaway
Para Windows 11 sem servidor, o único banco de grafos embutido, com Cypher, índice vetorial HNSW, FTS e algoritmos (Louvain/PageRank/WCC) que é mantido hoje é o **LadybugDB** (`pip install ladybug`, fork MIT do Kùzu — o Kùzu original foi arquivado em 2025-10-10 e `pip install kuzu` está congelado em 0.11.3). Para o caminho com servidor, o **Neo4j Community 2026.x** roda nativo no Windows (ZIP + JDK 21, sem Docker), tem o maior ecossistema GraphRAG (neo4j-graphrag, Graphiti, LightRAG, LlamaIndex, LangChain) e o GDS Community inclui todos os algoritmos (Leiden, Louvain, PageRank, similaridade, link prediction) limitado a 4 cores; **Memgraph** (Docker/WSL, BSL) é o fallback com MAGE (Leiden/Louvain/node2vec/GNN link prediction) e o Memgraph Lab.

### Inferences
- Para o volume previsto (2.900 notas iniciais + 50–300 itens/dia ≈ 20–110 mil itens/ano, cada um gerando dezenas de entidades/arestas), qualquer uma das opções embutidas (LadybugDB) ou single-instance (Neo4j CE, Memgraph) cabe folgadamente em um laptop; já o AuraDB Free (200k nós/400k rel.) provavelmente estoura em 1–2 anos e o auto-pause de 72 h é incompatível com "local-first".
- O risco do LadybugDB é de governança (fork com ~13 meses, 1.9k estrelas, owner único no PyPI "adsharma"), não técnico: o formato é o do Kùzu, há wheels Windows oficiais, releases semanais e adoção por Cognee e LlamaIndex. Mitigação: Cypher portável + exportação Parquet/CSV + extensão `neo4j` para migrar para Neo4j CE se necessário.
- Neo4j CE em ZIP no Windows é a melhor opção "servidor sem Docker": JDK 21 + um serviço Windows; e é o único banco suportado nativamente por *todos* os frameworks avaliados (neo4j-graphrag, Graphiti, LightRAG, LlamaIndex, LangChain, Cognee).
- FalkorDB perde no Windows (lite exige WSL; servidor só Docker), na licença (SSPL) e em algoritmos (sem Louvain/Leiden). ArangoDB, TigerGraph, TypeDB e Dgraph não oferecem binários Windows nativos e/ou não usam Cypher; Apache AGE exige Postgres (Docker no Windows) e Cypher parcial. SurrealDB embutido é viável tecnicamente, mas sem Cypher, sem algoritmos de grafo e sem transações no modo embutido.

## KQ2 — Frameworks GraphRAG / KG temporal: versões, backends, suporte a Anthropic, custo, ingestão incremental, ontologia custom, português

### Takeaway
Nenhum framework entrega sozinho o combo "ontologia própria + validade temporal + proveniência + ingestão diária + Claude": o **Graphiti** (0.31.2, Apache-2.0) é o único com arestas bi-temporais, resolução de entidades em cascata e tipos Pydantic customizados, com cliente Anthropic nativo, mas só suporta Neo4j/FalkorDB/Neptune (Kuzu deprecado, LadybugDB em RFC) e custa ~6–10 chamadas LLM por episódio; o **neo4j-graphrag** (1.23.0) tem `AnthropicLLM` com structured output, `SimpleKGPipeline`, resolvers e retrievers maduros, mas é Neo4j-only e sem modelo temporal; **LightRAG** (1.5.7, MIT) é o mais barato e multilingue (`SUMMARY_LANGUAGE`) com APIs de edição/merge e remoção por documento, porém seu adaptador Anthropic é defasado (sem JSON mode) e o esquema é fixo (entity_type/description/keywords); **Microsoft GraphRAG** (3.3.0) é batch-first, caro e tem `update` incremental só via CLI/LiteLLM.

### Inferences
- Suporte "nativo" a Anthropic hoje: Graphiti (`anthropic_client.py` + extra), neo4j-graphrag (`AnthropicLLM` com structured output), Cognee (via LiteLLM/instructor, extra `anthropic`), MS GraphRAG (via LiteLLM `model_provider: anthropic`), LlamaIndex (`llama-index-llms-anthropic`, não verificado nesta sessão), LightRAG (adaptador próprio, mas sem JSON mode e defaults de modelo obsoletos — funciona passando `llm_model_name`). Nenhum deles fornece embeddings Anthropic (não existem); é preciso Voyage, OpenAI, Gemini, Ollama ou `sentence-transformers` local.
- Encaixe com ingestão diária + ontologia própria + Claude: Graphiti é o mais próximo (tipos Pydantic, temporalidade, dedup, episódios como proveniência), mas amarra o grafo ao seu esquema interno (`Entity`/`RELATES_TO`/`Episodic`/`Community`) e a Neo4j/FalkorDB; neo4j-graphrag é o kit mais limpo para montar *seu* esquema em Neo4j (schema dict + resolvers + retrievers) sem temporalidade; LightRAG é ótimo como "camada de leitura barata" (mix query, reranker, multilingue) mas seu esquema fixo não comporta `valid_from/invalid_at`, subtipos de Item nem proveniência fina além de `source_id/file_path`.
- Português: LightRAG (`addon_params["language"]="Portuguese"` / `SUMMARY_LANGUAGE`) e MS GraphRAG (`prompt-tune --language`) têm botão explícito; neo4j-graphrag aceita `prompt_template` custom; Graphiti não expõe parâmetro de idioma (prompts em inglês, mas o Claude extrai em PT sem problema — inferência).
- Custo relativo (inferência a partir das contagens de chamadas): Graphiti ≈ 6–10 chamadas LLM/episódio; neo4j-graphrag ≈ 1 chamada por chunk (+ opcional extração de schema) + resolvers determinísticos; LightRAG ≈ 1–2 chamadas por chunk + gleaning + sumarização de entidades mescladas; MS GraphRAG é o mais caro (extração + sumarização por entidade + relatórios de comunidade por nível) — o próprio projeto avisa.

### Gaps
- Nenhum benchmark 2025–2026 encontrado compara Graphiti com LightRAG/MS GraphRAG lado a lado; o GraphRAG-Bench não nomeia sistemas no abstract.
- Custo oficial por episódio do Graphiti (tokens/US$) não é publicado; a estimativa de 6–10 chamadas vem de um mirror de docs.
- Não confirmei se o `LLMGraphTransformer` do LangChain foi de fato movido para `langchain-neo4j` (a descrição do pacote o cita, mas o README não).
- Documentação do grafo semântico do txtai (404 nos caminhos tentados) — não avaliado.

## KQ3 — Resolução de entidades, enforcement de esquema, atualização incremental, proveniência, validade temporal, score de importância/decaimento, controle de custo

### Takeaway
A cascata usada pelo Graphiti (exato normalizado → MinHash/LSH com Jaccard ≥ 0,9 → candidatos por embedding com cosseno ≥ 0,6 → juiz LLM com saída estruturada) é o padrão de referência barato para dedup incremental e pode ser reimplementada em ~200 linhas sobre qualquer banco; enforcement de esquema deve vir de Pydantic + saída estruturada do Claude (Haiku 5.5 para extração a US$0,10/MTok de entrada; Sonnet 5.5 para julgar merges e sintetizar; Fable 5.1 só para geração de ideias), com Batch API (−50%) e cache de prompt (0,1× leitura) para o backlog de 2.900 notas.

### Cited Findings
- Graphiti `resolve_extracted_nodes`: colapsa duplicatas exatas do mesmo lote (prefere label mais específico e nome mais longo); candidatos por propriedades de identidade (`identity_properties`), nome exato normalizado (`EntityNode.get_by_names`) e busca semântica (`node_similarity_search`, cosseno ≥ 0,6, até 15 candidatos por fonte); resolução determinística, depois juiz LLM com prompt `dedupe_nodes.nodes` e saída `NodeResolutions` (sumários truncados a 120 chars, `max_tokens` 16384, guardas contra IDs inválidos); nós não resolvidos mantêm identidade nova — [node_operations.py](https://raw.githubusercontent.com/getzep/graphiti/main/graphiti_core/utils/maintenance/node_operations.py). Camada determinística: `_normalize_string_exact` (lowercase/trim), gate de entropia (`_NAME_ENTROPY_THRESHOLD` 1.5, `_MIN_NAME_LENGTH` 6, `_MIN_TOKEN_COUNT` 2), shingles de 3 caracteres, MinHash com 32 permutações em bandas de 4 (8 bandas), Jaccard ≥ `_FUZZY_JACCARD_THRESHOLD` 0.9; senão vai ao LLM — [dedup_helpers.py](https://raw.githubusercontent.com/getzep/graphiti/main/graphiti_core/utils/maintenance/dedup_helpers.py).
- neo4j-graphrag: resolvers `SinglePropertyExactMatchResolver` (mesmo label + mesmo `name`), `FuzzyMatchResolver` (RapidFuzz), `SpaCySemanticMatchResolver` (cosseno); rodam após cada execução; `filter_query` exclui entidades de execuções anteriores; constraints `EXISTENCE`/`KEY` no esquema podam extrações inválidas — [KG builder guide](https://neo4j.com/docs/neo4j-graphrag-python/current/user_guide_kg_builder.html).
- LightRAG: `merge_entities` (alvo existente ou novo nome normalizado), `edit_entity` com rename migrando relações, peso de relação ≥ número de `source_id` distintos (evidência), `adelete_by_doc_id` reconstrói entidades ainda suportadas por outros documentos — [ProgramingWithCore.md](https://raw.githubusercontent.com/HKUDS/LightRAG/main/docs/ProgramingWithCore.md).
- Literatura: DEG-RAG avalia sistematicamente blocking, embeddings, métricas e merge para ER em KGs gerados por LLM; "drastically reduces graph size" e melhora QA em vários GraphRAGs — [arXiv 2510.14271](https://arxiv.org/abs/2510.14271). "Match, Compare, or Select?" (COLING 2025): estratégia de *seleção* (com interação entre registros) é a mais eficaz; framework composto ComEM melhora eficácia e custo — [arXiv 2405.16884](https://arxiv.org/abs/2405.16884). LLM-CER (PVLDB vol. 19): clustering in-context reduz chamadas vs. pareamento; LSH foi o melhor blocking — [PVLDB p4746](https://www.vldb.org/pvldb/vol19/p4746-ke.pdf) **[PDF não parseado; resumo via busca]**.
- Validade temporal: Graphiti marca fatos como inválidos em vez de apagar e invalida automaticamente contradições ("bi-temporal") — [README](https://raw.githubusercontent.com/getzep/graphiti/main/README.md); `remove_episode` preserva fatos reafirmados por outros episódios — [release v0.31.2](https://api.github.com/repos/getzep/graphiti/releases/latest).
- Proveniência: neo4j-graphrag mantém `Document(path)`→`Chunk(text, embedding)` com `FROM_DOCUMENT`/`NEXT_CHUNK` e liga entidades aos chunks — [KG builder guide](https://neo4j.com/docs/neo4j-graphrag-python/current/user_guide_kg_builder.html); LightRAG guarda `source_id`/`file_path` em entidades e relações — [ProgramingWithCore.md](https://raw.githubusercontent.com/HKUDS/LightRAG/main/docs/ProgramingWithCore.md); MS GraphRAG embeda `text_unit_text`, `entity_description`, `community_full_content` e grava tabelas Parquet — [YAML config](https://microsoft.github.io/graphrag/config/yaml/).
- Decaimento/importância: FadeMem (jan/2026) usa decaimento exponencial adaptativo modulado por relevância semântica, frequência de acesso e padrões temporais, hierarquia de duas camadas, consolidação guiada por LLM, −45% de armazenamento — [arXiv 2601.18642](https://arxiv.org/abs/2601.18642); implementação prática com k = 0,03 (meia-vida ≈ 23 dias) e boost de importância em faixa estreita para não abafar a similaridade vetorial — [callsphere blog](https://callsphere.ai/blog/temporal-memory-decay-agents-forget-irrelevant-information.md) **[secundário]**.
- Preços Anthropic (USD/MTok, entrada/saída): Claude Fable 5.1 $10/$50 (cache read $0,25); Claude Opus 5.5 $4/$20; Claude Sonnet 5.5 $2/$10 (cache read $0,10); Claude Haiku 5.5 $0,10/$0,50 até 100k tokens de prompt ($0,50/$2,50 acima); Batch API −50% (Haiku 5.5 $0,05/$0,25; Sonnet 5.5 $1/$5; Fable 5.1 $5/$25); cache write 1,25× (5 min) / 2× (1 h); cache read 0,1× (0,05× em Opus/Sonnet 5.5; 0,025× em Fable 5.1); descontos de batch e cache se combinam — [Anthropic pricing](https://platform.claude.com/docs/en/about-claude/pricing).
- Embeddings Voyage (recomendados para uso com Claude): `voyage-4-lite` $0,02/MTok, `voyage-4` $0,06, `voyage-4-large` $0,12; rerankers `rerank-3` $0,05, `rerank-3-lite` $0,02; primeiros 200 M tokens grátis por conta; batch −33% — [Voyage pricing](https://docs.voyageai.com/docs/pricing).
- Saída estruturada no Claude: `output_config.format` / `client.messages.parse()` e `strict: true` em tools (referência local do skill `claude-api`, cache 2026-10-06) — [Structured outputs docs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs) **[URL não aberta nesta sessão]**; neo4j-graphrag e Graphiti confirmam suporte a structured output no Anthropic (citações acima).

### Inferences
- Pipeline de ER recomendado (reimplementável em qualquer banco): (1) chave canônica por tipo (`doi`, `arxiv_id`, `github_full_name`, `url` normalizada, `handle` Instagram) → merge determinístico; (2) nome normalizado exato; (3) MinHash/LSH + Jaccard ≥ 0,9 (ou RapidFuzz ≥ 92) só para nomes com entropia suficiente; (4) k-NN por embedding (cosseno ≥ 0,85 para Technique/Problem, ≥ 0,6 só como *blocking*); (5) juiz LLM apenas para pares ambíguos, em lote, com estratégia "select among candidates" (mais eficaz que match binário, conforme COLING 2025) e saída estruturada; registrar `merged_from` e `resolution_method` como proveniência da decisão.
- Enforcement de esquema: declarar a ontologia como modelos Pydantic (um por label, `Literal` para enums e tipos de relação permitidos por par de labels), usar `messages.parse()` com Haiku 5.5 e validar duas vezes (Pydantic + checagem de padrões `(src_label, rel, tgt_label)` antes do write) — mesmo princípio de `SchemaLLMPathExtractor(strict=True)` e dos `patterns` do neo4j-graphrag.
- Incremental: tratar cada item como "episódio" (hash de conteúdo + `source_id`), gravar `Chunk`s e `MENTIONS` antes de resolver, e rodar comunidade/PageRank em job noturno (não a cada insert); ao reprocessar um item, invalidar (não apagar) arestas antigas (`invalid_at`) — padrão Graphiti.
- Estimativa de custo (aritmética própria sobre os preços citados): extração com Haiku 5.5 ≈ 2k tokens entrada + 800 saída por item ≈ $0,0006/item; com dedup/juiz em Sonnet 5.5 para ~20% dos itens (+$0,01) e sumário PT em Haiku, ≈ $0,003/item → 300 itens/dia ≈ $0,9/dia (~$27/mês); backlog de 2.900 notas via Batch API ≈ $5–10; embeddings de 300 itens/dia (~600k tokens) ≈ $0,01/dia no `voyage-4-lite` e cobertos pela cota grátis de 200 M tokens por ~1 ano. Geração de ideias com Fable 5.1 é o único custo relevante: a $10/$50, um ciclo diário de 50k entrada/5k saída ≈ $0,75/dia.
- Score de importância sugerido (inferência a partir de FadeMem + práticas citadas): `importance = w1·relevance_score + w2·novelty + w3·pagerank_norm + w4·log1p(access_count) + w5·exp(−λ·dias_desde(last_seen))`, com λ reduzido para entidades de alta importância; usar como *boost* limitado (ex.: ×[0,8; 1,2]) sobre o score híbrido de recuperação, nunca como filtro duro.

### Gaps
- Não há dados publicados de precisão/recall dos resolvers do neo4j-graphrag nem da cascata do Graphiti em corpora técnicos em português.
- Não encontrei artigo ou implementação de referência para "importância/decaimento" aplicado a grafos pessoais de conhecimento (as fontes tratam de memória de agentes conversacionais).
- Thresholds do `FuzzyMatchResolver` e exemplo de `identity_properties` do Graphiti não foram verificados.

## KQ6 — Ontologia proposta para o domínio (IA × medicina, itens heterogêneos, motor de ideias)

### Takeaway
Modelar com um label base `Item` (fonte ingerida, com subtipos como labels adicionais) separado dos nós "semânticos" (`Technique`, `Problem`, `ClinicalDomain`, `Organization`, `Person`, `Model`, `Dataset`, `Regulation`, `Trend`) e dos nós "derivados" (`Claim`, `Idea`, `Community`), com proveniência sempre via `Chunk`/`Episode` e validade temporal em todas as arestas semânticas; isso é compatível com o grafo lexical do neo4j-graphrag, com os tipos Pydantic do Graphiti e pode ser exportado para o esquema plano do LightRAG quando necessário.

### Cited Findings
- Graphiti: nós `EntityNode` com `uuid, name, group_id, labels, created_at, summary, attributes, name_embedding`; tipos customizados Pydantic por entidade e por aresta, `edge_type_map` por par de tipos — [Custom types](https://help.getzep.com/v2/graphiti/core-concepts/custom-entity-and-edge-types.md); arestas com `valid_at`/`invalid_at`/`created_at` — [zby review](https://zby.github.io/commonplace/sources/graphiti-temporal-knowledge-graph) **[secundário]**; comunidades como `CommunityNode` com sumário e embedding do nome — [community_operations.py](https://raw.githubusercontent.com/getzep/graphiti/main/graphiti_core/utils/maintenance/community_operations.py).
- LightRAG: entidade = `entity_name, entity_type, description, source_id, file_path`; relação = `src_id, tgt_id, description, keywords, weight, source_id, file_path` — [ProgramingWithCore.md](https://raw.githubusercontent.com/HKUDS/LightRAG/main/docs/ProgramingWithCore.md).
- neo4j-graphrag: esquema como `node_types` (label, description, properties), `relationship_types`, `patterns` (src, rel, tgt), flags `additional_*`, constraints `EXISTENCE`/`KEY`; grafo lexical `Document`→`Chunk` (`FROM_DOCUMENT`, `NEXT_CHUNK`) e entidades `__Entity__` ligadas a chunks — [KG builder guide](https://neo4j.com/docs/neo4j-graphrag-python/current/user_guide_kg_builder.html).
- MS GraphRAG: níveis de comunidade (Leiden via graspologic), `community_reports` por nível, embeddings de `entity_description` e `community_full_content` — [YAML config](https://microsoft.github.io/graphrag/config/yaml/); [PyPI graphrag](https://pypi.org/pypi/graphrag/json).
- Neo4j: índices vetoriais em nós e relacionamentos, 1–4096 dimensões — [Vector indexes](https://neo4j.com/docs/cypher-manual/current/indexes/semantic-indexes/vector-indexes/); LadybugDB: índice vetorial só em propriedades de nós — [docs/extensions/vector](https://docs.ladybugdb.com/extensions/vector).

### Inferences
Proposta (labels em PascalCase, relações em UPPER_SNAKE, propriedades em snake_case):

- **Nós de fonte** — `Item` (+ um label de subtipo: `Paper`, `Article`, `NewsletterItem`, `InstagramPost`, `Repo`, `MCPServer`, `Skill`, `Product`) com `id` (canônico: `doi`/`arxiv_id`/`github_full_name`/URL normalizada/`ig_shortcode`), `title`, `url`, `source` (feed/newsletter/handle), `published_at`, `ingested_at`, `summary_pt`, `summary_en`, `relevance_score`, `novelty`, `importance`, `embedding` (título+resumo), `raw_hash`, `obsidian_path` (legado), `seen_id`. `Chunk` (`text`, `embedding`, `order`) com `(:Chunk)-[:FROM_ITEM]->(:Item)` e `[:NEXT_CHUNK]`.
- **Nós semânticos** — `Technique` (ex.: "retrieval-augmented generation", "federated learning"), `Model` (`family`, `params`, `license`, `release_date`), `Dataset`, `Problem` (job-to-be-done clínico/operacional; `stakeholder`), `ClinicalDomain` (especialidade/condição; `snomed`/`mesh` opcional), `Organization`, `Person` (`role`, `handle`), `Regulation` (`jurisdiction`, `effective_from`), `Trend` (`window_start/end`, `velocity`). Todos com `name`, `aliases[]`, `description_pt`, `embedding`, `created_at`, `last_seen_at`, `mention_count`, `pagerank`, `community_id`, `importance`, `merged_from[]`.
- **Nós derivados** — `Claim` (`text`, `polarity`, `confidence`, `evidence_level`), `Idea` (`title`, `hypothesis_pt`, `status`, `novelty`, `feasibility`, `generated_by_model`, `created_at`), `Community` (`level`, `summary_pt`, `algorithm`, `run_id`), `Episode` (uma execução de ingestão: `run_id`, `started_at`, `model`, `prompt_version`, `cost_usd`).
- **Relações** (todas com `created_at`, `valid_from`, `invalid_at`, `source_chunk_ids[]`, `extracted_by` (modelo+prompt_version), `confidence`): `Item-[:MENTIONS]->Semântico`, `Item-[:USES_TECHNIQUE]->Technique`, `Item-[:PROPOSES]->Technique|Model`, `Item-[:ADDRESSES_PROBLEM]->Problem`, `Item-[:IN_DOMAIN]->ClinicalDomain`, `Item-[:CITES]->Item`, `Item-[:DERIVED_FROM]->Item` (fork, versão, repost), `Item-[:PUBLISHED_BY]->Organization|Person`, `Item-[:SIMILAR_TO]->Item` (`score`, calculado, sem LLM), `Item-[:EVALUATED_ON]->Dataset`, `Claim-[:EVIDENCE_FOR|CONTRADICTS]->Claim|Idea`, `Claim-[:STATED_IN]->Item`, `Technique-[:SUPERSEDES]->Technique`, `Model-[:SUPERSEDES]->Model`, `Regulation-[:GOVERNS]->ClinicalDomain|Technique`, `Idea-[:INSPIRED_BY]->Item|Claim|Community`, `Idea-[:COMBINES]->Technique`, `Idea-[:TARGETS]->Problem`, `Semântico-[:MEMBER_OF]->Community`, `Item-[:INGESTED_IN]->Episode`, `Person-[:AFFILIATED_WITH]->Organization`, `Trend-[:COMPOSED_OF]->Technique|Problem`.
- **Padrões permitidos** (`patterns` no sentido do neo4j-graphrag / `edge_type_map` no Graphiti): lista explícita de triplas acima; tudo fora dela é rejeitado ou rebaixado para `RELATED_TO` com `needs_review=true`.
- **Temporalidade**: `valid_from` = data de publicação do item que originou o fato (não a data de ingestão); `invalid_at` setado por `SUPERSEDES`, por contradição detectada entre `Claim`s ou por decaimento (`last_seen_at` antigo + `importance` baixa) — nunca deletar.
- **Comparação**: o esquema do Graphiti cabe como *camada episódica* (cada `Item` = episódio; `Entity` ↔ nós semânticos; `RELATES_TO{fact}` ↔ relações tipadas via `edge_type_map`), mas o Graphiti não tem subtipos de item, `Claim`/`Idea` nem scores — teriam de ser `attributes`. O LightRAG achata tudo em `entity_type`+`description`+`keywords`, perdendo tipagem de aresta, temporalidade e scores: útil apenas como índice de leitura derivado. O neo4j-graphrag expressa exatamente este esquema (`node_types`/`relationship_types`/`patterns`) e já fornece `Document/Chunk` para proveniência.

### Gaps
- Não há ontologia pública consolidada para "IA × medicina + curadoria pessoal"; a proposta é inferência. Vocabulários externos (MeSH/SNOMED para `ClinicalDomain`, Papers-with-Code para `Technique`) não foram verificados nesta sessão.

### Inferences
- **Por que LadybugDB como primário**: é o único que satisfaz simultaneamente "sem servidor", "Windows nativo", "Cypher", "vetor + FTS + Louvain/PageRank no mesmo arquivo" e "licença MIT"; a carga prevista cabe em um único arquivo `.lbdb`; LlamaIndex e Cognee já o suportam, e o esquema proposto (KQ6) é gravado por Cypher próprio, sem depender de framework. Risco: fork jovem (governança); mitigação: export Parquet nightly + extensão `neo4j` + Cypher portável, com Neo4j CE como fallback testado.
- **Por que Neo4j CE como fallback/upgrade (e não Memgraph)**: roda nativo no Windows sem Docker (ZIP + JDK 21), GPL-3.0 sem restrição de uso, GDS CE com todos os algoritmos (Leiden, node similarity, link prediction, FastRP) em 4 cores, índice vetorial com `SEARCH` e quantização, e é o único backend comum a neo4j-graphrag, Graphiti, LightRAG, LlamaIndex, LangChain e Cognee — se o motor de ideias exigir Graphiti, só Neo4j (ou FalkorDB) serve. Memgraph fica em segundo por exigir Docker/WSL e BSL, embora o MAGE seja tecnicamente ótimo.
- **Camada LLM (ambos os caminhos)**: Haiku 5.5 para extração/classificação/sumário PT com `messages.parse()` + Pydantic (custo ≈ $0,001/item); Sonnet 5.5 para juiz de dedup, verificação de claims e sumários de comunidade; Fable 5.1 (ou Opus 5.5 a $4/$20) só no ciclo de geração de ideias sobre contexto já recuperado; Batch API para backlog e jobs noturnos; cache de prompt para o system prompt da ontologia (1h TTL durante batches).
- **Embeddings**: `voyage-4-lite` (1024-d, $0,02/MTok, 200 M grátis) para `Item`/`Chunk`/entidades; alternativa offline `sentence-transformers` (`bge-m3`, multilingue — citado pelo LightRAG) rodando em CPU para independência total.
- **Algoritmos**: LadybugDB `algo` cobre Louvain/PageRank/WCC; Leiden, node similarity e link prediction via export para `igraph`/`leidenalg` ou NetworkX em job noturno (grafo de ~10⁵ nós cabe em memória); no caminho B, GDS CE faz tudo in-database.
- **Reuso de frameworks como componentes (não como esqueleto)**: `neo4j-graphrag` só no caminho B; `FuzzyMatchResolver`/cascata do Graphiti reimplementada (KQ3); LightRAG opcional como índice de leitura "mix" sobre um export plano (`insert_custom_kg`) para perguntas abertas; MS GraphRAG não recomendado (batch-first, caro, Python <3.14).
- **Não recomendados**: AuraDB Free como primário (auto-pause 72 h, exclusão após 30 d, 200k/400k); Kùzu (arquivado); FalkorDB (SSPL + Docker/WSL + sem Louvain); ArangoDB/TigerGraph/TypeDB/Dgraph (sem Windows nativo e/ou sem Cypher); AGE (Postgres em Docker, Cypher parcial); SurrealDB (sem Cypher/algoritmos).
